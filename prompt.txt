
u are a Senior Software Architect and Full-Stack Laravel/Vue/Nuxt Engineer.

Build a production-ready MVP for a price and product-condition alert platform.

The platform allows users to:

1. Submit a product URL from Torob.
2. Configure one or more conditions such as:
   - Minimum price
   - Maximum price
   - Price range
   - Product availability
   - Stock status
   - Seller/shop name
   - JSON/API field values
   - HTML element values, if the source legally permits HTML fetching
3. Configure a notification channel such as SMS.
4. The system periodically checks the source.
5. If the configured conditions are satisfied, the system sends a notification.
6. The notification must be deduplicated and must not be sent repeatedly unless the state changes or the user explicitly configures repeated notifications.

The system must be extensible for future providers such as Divar and other marketplaces.

The primary architecture must be:

- Domain-Driven Design
- SOLID
- DRY
- Modular Monolith
- Workflow-based
- Adapter-based external integrations
- Testable and maintainable
- Resource-efficient for MVP
- Security-first
- API-first

Do not implement the entire system in one step. Work phase by phase. At the end of each phase:
- Run tests
- Run static analysis
- Run formatting
- Report changed files
- Report known limitations
- Wait for approval before starting the next phase unless explicitly instructed otherwise.

8. ALERT STATE AND DEDUPLICATION
==================================================

Avoid sending duplicate SMS messages.

Implement state transitions:

- condition_not_met
- condition_met
- notification_pending
- notification_sent
- notification_failed
- resolved

Default behavior:

- Send notification only when a condition changes from false to true.
- Do not send every time the scheduler runs.
- If the condition becomes false and later true again, allow a new notification.
- Support optional cooldown in minutes.
- Support optional repeat notification interval.
- Support a maximum notification count per day.
- Store a deterministic event_key.

Example event_key:

sha256(
    watch_id
    + workflow_id
    + condition_state
    + normalized relevant values
)

Use database constraints and idempotency locks to prevent duplicate notifications under concurrent workers.

# فاز ۳ — لایهٔ اجرای کار روی سایت (بعد از تأیید من شروع کن)
هدف: «در هر سایتی که بخواهم کاری که می‌گویم انجام بده».
- یک interface به نام `SiteAction` با `supports(url)`, `plan(context)`, `execute(plan)`.
- اجرا با Playwright (Node sidecar) — نه curl برای فرم‌های JS-دار.

- شروع با یک اکشن واقعی: «افزودن محصول به سبد ترب» به‌صورت dry-run.
